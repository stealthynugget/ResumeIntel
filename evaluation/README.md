# Evaluation protocol

The Kaggle resume dataset provides job-family categories, not candidate-to-JD relevance labels. Category agreement is therefore not used as matching accuracy.

Run the three demo JDs against the full local corpus with `python -m evaluation.smoke`. The run analyzes 30 candidates per JD and shows 10. Build an 18-candidate review pool per JD with `python -m evaluation.baseline`: it interleaves hybrid and keyword-only ranks to select 16 distinct candidates, then adds two unrelated profiles. The raw review pool is local and ignored because it contains resume previews. `review_pool_manifest.json` is a frozen, text-free record of the judged candidates and the two methods' top-five rankings. `labels.csv` stores the 54 manually assigned 0–3 judgments and reasons without source text. The script `python -m evaluation.score_labels` uses the frozen manifest to recompute the reported Precision@5 and pool-relative nDCG@5 from the submission ZIP without requiring local resume data. A relevance grade of 2 or 3 counts for Precision@5.

The implementer reviewed previews and investigated uncertain cases in full source documents **after viewing rankings**. These judgments are not blind or independently reviewed. nDCG uses each role's 18 judged candidates as its ideal ranking, not the entire corpus. The judged pool is useful for a demo comparison; it cannot establish corpus-wide recall or hiring validity. The HR regression is reported, not omitted.

`python -m evaluation.audit_claims` checks exact quote/span/source integrity for 15 manually selected assessment claims in `claim_audit.csv`. The separate `semantic_judgment` column records whether the context actually supports the requirement, is correctly uncertain, or is only a mention. That human judgment is not inferred from the quote check. See `report.md` for observed results.

Reproduce corpus and performance checks with `python -m evaluation.verify_full_import`, `python -m evaluation.coverage`, and `python -m evaluation.benchmark`. The verification expects the primary CSV in `data/source/` and the existing local database. The first import's row outcomes are preserved even after repeat uploads. The implementation and labels can be inspected without distributing raw resumes.

The authenticated `/api/evaluation` endpoint serves these saved, text-free JSON artifacts to the React evaluation page. `full_browser_smoke_results.json` records a local Chrome flow through sign-up, dashboard, evaluation, matching, evidence-only AI review/chat fallback, exact citation passage, sign-out, and sign-in. Its numbers do not add new relevance judgments or update the original ranking measurements. A live gateway chat returned one validated citation; this checks integration and citation identity, not all possible model claims.

`quality_browser_smoke_results.json` records the focused follow-up Chrome pass: scoped recruiter dashboard counts, the correctly labeled mean of saved role medians, the visible 18-per-role Evaluation disclosure and HR regression, a live Python-only AI draft, an unsupported salary fallback, exact citation loading and highlighting, the stale-run selection guard, and mobile-width checks. It contains UI metadata only. The saved rankings and benchmarks were not recomputed by this browser test.
`recruiter_chat_browser_smoke_results.json` records the later assistant flow across general, corpus, and candidate scopes, including signed-in citation deep links, saved score explanation, and mobile width. It is metadata-only and does not update the earlier 2,484-record rankings or judgments. Two further private PDFs were uploaded after the first one; the October 1 local database has 2,487 candidates and 22,921 spans/FTS entries. The Evaluation page reads that live count separately from the saved benchmark snapshot.

`retrieval_audit_v1.json` was produced by `python -m evaluation.retrieval_audit`. It reads the current database without creating match runs and records FTS span hits, unique candidates within the 3,000-hit cap, first-call and five warm-call retrieval latencies, process peak RSS, and environment details. It measures the unchanged retrieval method on the 2,487-candidate database. It is not an alternative-ranker evaluation; no newly surfaced candidates were labeled or claimed as improvements.

The saved browser metadata verifies five example recruiter questions and distinct gateway fallback paths. There is **no labeled chatbot question benchmark** yet, so these tests establish behavior, not answer accuracy or refusal rates. `report.md` distinguishes the 144 automated source-link checks, the separate 15-claim semantic audit, and the seven-item gap/status spot check.
# Live category coverage in the app

The Evaluation page requests live candidate and indexed-span counts for every accessible dataset category from `/api/evaluation`. These are indexing coverage diagnostics. Recruiter accounts see only shared CSV records and their own uploads; admins can inspect all candidates.

`category_proxy_results.json` is a separate, reproducible 24-category retrieval diagnostic over 2,481 shared CSV resumes. For each dataset category, `python -m evaluation.category_proxy` queries the category title through FTS5 and hybrid MiniLM+FTS5 retrieval and grades the top five by exact category-label agreement. These binary labels are weak proxies and do not establish resume relevance to a real job description, skill evidence, hiring accuracy, or fairness. The three saved 18-candidate manually judged role comparisons remain the only JD relevance results.
